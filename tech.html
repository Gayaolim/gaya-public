Start here

This page is for whoever maintains the code — not for the team running Gaya's day-to-day community operations. Anything involving a terminal, a script, or an environment variable lives here, not in the Team Playbook.

If you're new to this project: read this page top to bottom once, then use it as a reference. The actual source of truth for code is the gaya-automation GitHub repo (private) — this page orients you, it doesn't replace reading the code.

Architecture

Airtable is the single source of truth the team actually touches. A Flask app on Railway is the automation layer — Airtable buttons call it over HTTP, it talks to Google Calendar/Groups, Zoom, and Brevo, and writes results back into Airtable.

Buttons in Airtable are Scripting extension scripts, not Automation "Run a script" steps — the two have different runtimes (no Secrets vault in Scripting, no "record that was clicked" binding, `output.text()` vs `console.log()`). See integrations/airtable/*.js for the actual scripts.

Manual & fallback scripts

These need a terminal and real Railway credentials — never ask the team to run one of these. If an operator needs the output, run it yourself and send them the result.

Breakout-room roster (manual placement fallback)

Prints who's assigned to which diversity-balanced group, for a live event where automated assignment needs a manual backup.

railway run --service "Gaya API" --environment production \
  python3 scripts/reporting/zoom_group_roster.py <event record ID> <group count>

General pattern — any one-off script against real data

Runs a script with real Railway env vars injected, without deploying it anywhere:

railway run --service "Gaya API" --environment production python3 <script.py>

Railway operations

⚠️
Never dump all variables at once (railway variables with no filter) — this project has a documented past incident of a secrets leak that way. Always grep for the one key you need: railway variables --service "Gaya API" --environment production | grep KEY_NAME.
  • Logs: railway logs --service "Gaya API" --environment production (or the get_logs Railway MCP tool, filterable by log_type: http and path)
  • Set a variable: railway variables --service "Gaya API" --environment production --set "KEY=value"
  • Redeploy: pushing to main auto-deploys — no manual redeploy step needed for the API service itself

Running the tests

source .venv/bin/activate
python -m unittest discover -s tests/acceptance -v

All tests use dependency injection (a fake service/session object, e.g. FakeZoomSession, FakeDirectoryService) rather than mocking requests directly — match this pattern for new tests.

Updating these pages

Both this page and the Team Playbook live in this repo (gaya-automation, private) at docs/index.html (playbook) and docs/tech.html (this page) — that's the source of truth, edit there and commit as usual.

⚠️
GitHub Pages needs a paid plan for private repos, so these pages are mirrored to the public gaya-public repo for hosting. After editing and pushing here, re-publish with the snippet below — the Contents API needs the target file's current sha on every update, not just the first create.
SHA=$(gh api repos/Dmitreyvladimirov/gaya-public/contents/playbook.html --jq .sha)
gh api repos/Dmitreyvladimirov/gaya-public/contents/playbook.html -X PUT \
  -f message="Update playbook" \
  -f content="$(base64 -i docs/index.html | tr -d '\n')" \
  -f sha="$SHA" -f branch="main"

SHA=$(gh api repos/Dmitreyvladimirov/gaya-public/contents/tech.html --jq .sha)
gh api repos/Dmitreyvladimirov/gaya-public/contents/tech.html -X PUT \
  -f message="Update tech reference" \
  -f content="$(base64 -i docs/tech.html | tr -d '\n')" \
  -f sha="$SHA" -f branch="main"

New images referenced from either page need the same treatment, uploaded to the matching assets/ path in gaya-public first.
